# Relay 数据保留

语言：简体中文 | [English](../../docs/relay-retention.md)

Relay 将可回收的投递正文与防止重复操作的必要证据分开。此策略保持
`iscp.relay.duplex.v1` 和 `submit.query` 返回的原签名回执不变。

| 数据 | 保留规则 |
| --- | --- |
| 成功写入传输连接且交付事务已提交的队列正文 | 下一轮清理即可回收；不代表接收端确认，不增加重新投递 |
| 尚未投递的队列正文 | 保留到 `expires_at`，不延长原截止时间 |
| 受理键、匹配字段和原签名 `receipt_raw` | 命名空间仍接收请求期间保留，正文过期后也保留 |
| 重复的 admission `receipt_canonical` JSON | migration 7 删除；没有读取方依赖该副本 |
| 未决控制操作、凭据历史及授权证据 | 按原恢复规则保留，本次正文清理不处理 |

Relay 启动时执行清理，之后每15秒执行一轮。每轮最多8个批次，每批最多256条，
总预算5秒，各批独立提交。被投递事务锁定的行会跳过。每批校验原writer epoch/role
及continuous history，只删除本scope/history存在admission的队列正文。
旧格式或无法解释的记录不会直接丢弃，后续批次超时也不会回滚已提交批次。

私有 `/metrics` 提供
`iscp_relay_payload_cleanup_{runs_total,batches_total,deleted_total,errors_total,last_success_unixtime}`。
失败会记录不含正文或凭据的通用告警。运维应同时查看成功时间是否停止推进、可清理积压、
数据库表大小和磁盘可用空间。15秒是调度目标，数据库不可用时不能保证最大滞留时间；
失败会重试，但不放宽写入围栏。

受理证据远小于正文，其键数量仍会增长。开放命名空间的唯一键不能随意套用TTL，否则旧消息ID
会被重新受理。后续进一步压缩也必须保留相同原回执和匹配语义；删除去重证据前，须按既有契约
永久关闭命名空间并隔离所有writer。

migration 7移除重复物理列。应先停Relay writer，保存数据库检查点及原回执指纹，再迁移并启用
不再写该列的新程序。旧程序不能直接回退使用迁移后的数据库。删列不会立即归还既有heap空间；
日常autovacuum负责复用已删空间，单次 `VACUUM FULL` 必须核算重写/WAL空间、安排维护窗口，
之后验证原回执和身份。不能将反复重写全表作为日常到期处理。

凭据和控制结果精简属于独立生命周期变更：历史token仍参与代次和路由判断，已完成控制结果还需
保留摘要、凭据最大有效期、前驱及未决ACK证据。不能仅因其中一个token到期就删除这些记录。
